1️⃣ مقارنة استراتيجيات عرض وبناء الصفحات (Rendering Strategies)

أهم مقارنة في الشيت كله (الأسئلة 3، 12، 13، 14، 15، 16، 17). الفرق كله بيدور حوالين: مين بيطبخ الصفحة؟ وإمتى؟

الطريقة فين بتتجهز؟ إمتى بتتجهز؟ (التوقيت) الـ SEO والسرعة المبدئية أفضل استخدام (أمثلة الشيت) مفتاح الحل في الامتحان 🔑
CSR
Client-Side Rendering		 جوه المتصفح (Browser) وقت الاستخدام بالـ JavaScript ضعيف في الـ SEO، وتفاعل لحظي سريع بدون تحميل الصفحة لوحة تحكم تفاعلية (Interactive Dashboard) أو SPA Highly interactive + Frequent API updates + Without full page reloads
SSR
Server-Side Rendering		 على السيرفر (Server) وقت طلب المستخدم بالظبط (At request time) ممتاز جداً في الـ SEO ودائماً يعرض أحدث داتا صفحة منتج عامة (Public product page) أسعارها بتتغير ومحتاجة SEO Generates on server + At request time + Frequently updated & SEO
SSG
Static Site Generation		 أثناء بناء المشروع (Build time) قبل ما أي مستخدم يطلب الصفحة (Before user requests) أسرع تسليم ممكن + أقل حمل على السيرفر + ممتاز للـ SEO مواقع التوثيق (Documentation website) والمدونات اللي نادر ما تتغير Changes infrequently + Before user requests + Minimal server processing
Hybrid Rendering مزيج حسب كل صفحة يجمع بين SSG و SSR و CSR ياخد مميزات كل طريقة في مكانها الصح متجر إلكتروني: الرئيسية SSG، المنتجات SSR، والداشبورد CSR تطبيق واحد يستخدم أكثر من استراتيجية ريندر معاً
Islands Architecture صفحة HTML ثابتة + جزر تفاعلية ثابتة مع تفعيل JS للجزر الصغيرة فقط خفيف جداً لأنه يقلل الـ JavaScript غير الضروري صفحة معظمها ثابت (Mostly static page) وفيها كام جزء تفاعلي بسيط Mostly static + Few interactive components + Minimize unnecessary JS

2️⃣ معماريات الأنظمة وتقسيم الواجهات (Application & Frontend Architectures)

الفرق بين تقسيم الطبقات أفقياً وتقسيم الفرق البرمجية رأسياً (الأسئلة 11، 18، 19، 20، 42).

🏢 Multi-Tier Architecture

  • فصل التطبيق إلى 3 طبقات أفقية مميزة (Distinct tiers):
  • 1. واجهة المستخدم (User Interface / Presentation).
  • 2. منطق البيزنس (Business Logic).
  • 3. إدارة قاعدة البيانات (Database Management).
UI + Business Logic + Database into distinct tiers

🧩 Micro Frontends

  • نفس فكرة الـ Microservices ولكن في الواجهة الأمامية (Frontend).
  • لما يكون التطبيق ضخم جداً وشغال عليه عدة فرق (Several teams).
  • كل فريق يبني ويحدث الجزء بتاعه (Frontend module) باستقلالية تامة.
Several teams + Independence + Frontend modules

🗺️ Architecture vs Framework

  • المعمارية (Architecture): هي القرارات التصميمية الكبرى والشاملة للنظام.
  • إطار العمل (Framework): هو الأدوات البرمجية اللي بننفذ بيها (Implementation capabilities).
  • معيار اختيار المعمارية: دائماً حسب متطلبات التطبيق والمفاضلات الهندسية (Requirements & Trade-offs).
Requirements and architectural trade-offs

3️⃣ مقارنة شاملة لبروتوكولات الـ APIs والاتصال اللحظي

إمتى نختار REST أو GraphQL أو gRPC أو WebSockets؟ (الأسئلة 2، 21، 25، 27، 28، 29، 30).

التقنية الفكرة الأساسية شكل البيانات والاتصال متى نستخدمها؟ علامتها في السؤال 🎯
REST متمحور حول الموارد وروابطها (Resource URLs) أوامر HTTP قياسية (GET, POST...) غالباً بصيغة JSON ثابتة الـ APIs القياسية لجلب أو تعديل الموارد عبر روابط واضحة Standardized HTTP methods and resource URLs
GraphQL الكلاينت يطلب الحقول اللي محتاجها بالمللي (Client-selected fields) استعلامات (Queries) تمنع جلب بيانات زيادة ملهاش لازمة تطبيقات الموبايل اللي بتحتاج تركيبات بيانات مختلفة في شاشات متعددة Minimizing unnecessary data retrieval + Client-selected fields
gRPC استدعاء دوال عن بُعد (Remote service methods) بعقود صارمة ثنائي سريع (Protocol Buffers) + يدعم التدفق (Streaming) التواصل الداخلي السريع بين الـ Internal Microservices Strongly typed contracts + Efficient serialization + Explicit contracts
WebSockets قناة اتصال مفتوحة ومستمرة في الاتجاهين (Full-Duplex) السيرفر والمتصفح يبعتوا لبعض في أي لحظة بدون انتظار طلب الشات اللحظي، الألعاب الأونلاين، التحديثات الفورية المزدوجة Continuous two-way communication
SSE
Server-Sent Events		 قناة في اتجاه واحد فقط من السيرفر للمتصفح السيرفر يبعت إشعارات أو تحديثات للمتصفح والعميل يستقبل فقط شريط أخبار أو أسعار أسهم بتتحدث من طرف السيرفر فقط اتجاه واحد (One-way server to browser)

4️⃣ تفاصيل الـ REST، أكواد HTTP، ومكونات GraphQL

أسئلة مضمونة في الامتحان (الأسئلة 22، 23، 24، 26، 29، 30).

🛠️ أوامر HTTP (PUT vs PATCH)

  • GET: قراءة وجلب بيانات فقط.
  • POST: إنشاء مورد جديد (Create new resource).
  • PUT: استبدال المنتج بالكامل (Complete replacement).
  • PATCH: تعديل جزئي (مثلاً تعديل السعر فقط بدون استبدال باقي بيانات المنتج).
Update ONLY price = PATCH

🚦 أكواد الاستجابة (HTTP Status Codes)

  • 200 OK: الطلب نجح بشكل عام.
  • 201 Created: تم إنشاء مورد جديد بنجاح (الأدق مع إنشاء الـ Resources).
  • 202 Accepted: استلمنا الطلب وجاري معالجته في الخلفية لسه مخلصش.
  • 204 No Content: نجح الطلب ومفيش محتوى راجع في الرد (مثل الحذف).
Creates a new resource = 201 Created

🧠 مبادئ REST & GraphQL

  • Stateless Communication: كل طلب لازم يحتوي على كل المعلومات اللازمة لمعالجته (السيرفر مش بيفتكر الطلبات القديمة).
  • GraphQL Resolver: هو الدالة المسؤولة فعلياً عن جلب أو حساب قيمة الحقل المطلوب.
  • GraphQL Schema: يوصف شكل وأنواع البيانات المتاحة فقط.
Retrieving value of a field = Resolver

📬 نماذج التواصل والأحداث

  • Asynchronous Communication: يبعت مهمة في الخلفية (Background task) ويكمل شغله والنتيجة توصل بعدين.
  • Event-Driven Architecture: خدمة الطلبات تنشر حدث (Publishes an event) فيشغل تحديث المخزن والإشعارات والتحليلات بشكل مستقل (Independently triggers).
Publishes event + Independently triggers = Event-Driven

5️⃣ تطور الويب، الأداء العالي، والذكاء الاصطناعي (Modern Web & AI)

ملخص أول 10 أسئلة في الشيت بالإضافة لسؤال التعلم الفيدرالي (38).

🚀 تطور الويب (Web Evolution)

  • الويب زمان كان مجرد عرض وتوصيل معلومات (Information delivery).
  • الويب الحديث اتطور نحو الحوسبة، الذكاء، واتخاذ الفعل (Computation, intelligence, and action).
  • Agentic Web: يتميز بأن الـ AI مش بس بيجاوب أسئلة، بل يفكر ويستخدم أدوات وينفذ أفعال (Reason, use tools, and perform actions).
Agentic Web = Reason + Tools + Actions

⚡ WebAssembly vs WebGPU

  • WebAssembly (Wasm): تشغيل كود ثقيل الحسابات (Computationally intensive code) بسرعة قريبة من لغة الآلة جوه المتصفح.
  • WebGPU: يتيح للمتصفح الوصول لكارت الشاشة (GPU capabilities) للرسومات المعقدة والحسابات المتوازية (Graphics & parallel computation).
Intensive code = Wasm | GPU & Parallel = WebGPU

📚 خطوات الـ RAG بالترتيب

  • عشان الـ LLM يجاوب بمصداقية من غير تأليف، بيمشي بالترتيب ده:
  • 1. Question (السؤال).
  • 2. Retrieval (البحث واسترجاع المعلومة من الداتابيز).
  • 3. Context (تجهيز السياق).
  • 4. LLM (إرسال السؤال والسياق للنموذج).
  • 5. Grounded Response (إجابة موثقة).
Question → Retrieval → Context → LLM → Grounded Response

🔒 AI في المتصفح & Federated Learning

  • تشغيل الـ AI قريب من المتصفح: يحسن بقاء البيانات محلياً (Data locality) ويقلل وقت تأخير الشبكة (Reduced network latency).
  • Federated Learning: تدريب نموذج الـ AI بالتعاون عبر عدة أجهزة (Collaboratively across devices) بدون نقل البيانات الخام (Raw data) لسيرفر مركزي للحفاظ على الخصوصية.
Train collaboratively without transferring raw data = Federated Learning

6️⃣ مقارنة طبقات الحوسبة: Edge vs Fog vs Cloud + Observability

تغطي الأسئلة من 31 إلى 40 بالكامل. التلات طبقات مش بيلغوا بعض، بل بيكملوا بعض (Complement one another) حسب متطلبات المهمة.

الطبقة المكان والدور المعماري المميزات الأساسية أمثلة الشيت العملية كلماتها المفتاحية في الامتحان 🔑
Edge Computing
الحوسبة الطرفية		 على الجهاز نفسه أو جنبه مباشرة (الكاميرا، الماكينة، العربية، حساس المريض) استجابة لحظية (Very low latency) + توفير الـ Bandwidth + يشتغل حتى لو النت قطع كاميرا تحلل الفيديو محلياً / مصنع يوقف ماكينة فوراً بدون نت / رصد العربيات Close to devices + Immediate local response + Reduced bandwidth
Fog Computing
الحوسبة الضبابية		 طبقة وسيطة موزعة (Intermediate layer) بين الـ Edge والـ Cloud تجميع البيانات وتنسيقها على مستوى إقليمي أو بين أقسام قريبة سيرفرات إقليمية تجمع بيانات تقاطعات المرور وتنسق الإشارات / تجميع بيانات أقسام المستشفى Intermediate processing & coordination + Regional servers aggregate data
Cloud Computing
السحابة المركزية		 مراكز بيانات مركزية ضخمة وبعيدة قدرة تخزين وحوسبة هائلة للتحليلات التاريخية وتدريب الذكاء الاصطناعي تخزين السجلات التاريخية للمرضى مركزياً / تحليلات المرور التاريخية وتدريب نماذج AI Historical records/analytics + Large-scale AI training

🔍 مبدأ المراقبة (Observability - س31)

  • عشان نفهم سلوك أي نظام موزع ونحقق في الأعطال، بنعتمد على 3 ركائز معاً:
  • 1. Logs (سجلات الأحداث النصية).
  • 2. Metrics (أرقام ومؤشرات الأداء مثل الرام والـ CPU).
  • 3. Traces (تتبع مسار الطلب بين الخدمات).
Logs + Metrics + Traces = Observability

⚖️ معايير توزيع المهام (Workload Placement - س39، س40)

  • بنقرر المهمة تشتغل على Edge ولا Fog ولا Cloud بناءً على:
  • الـ Latency، والـ Bandwidth، وقدرة المعالجة (Computing capacity)، والخصوصية (Privacy)، وحالة الاتصال (Connectivity).
  • المبدأ الأساسي هو: توزيع أحمال العمل حسب متطلبات المعالجة والتنسيق.
Distributing workloads according to requirements

7️⃣ الحوسبة بدون خادم (Serverless) والبلوكتشين (Blockchain & Web3)

تغطي آخر 10 أسئلة في الشيت (من 41 إلى 50) + السؤال 5.

⚡ Serverless Computing (س5، س41، س42، س43)

  • المفهوم (س5): مش معناها مفيش سيرفرات فيزيائية! معناها المطور بيشغل الدوال (Functions) بـ اهتمامات أقل بإدارة السيرفرات (Fewer server-level management concerns).
  • التوفير المالي (س41): للمهام المتقطعة السريعة، نستخدم On-demand serverless function with usage-based billing عشان مندفعش في سيرفر شغال 24 ساعة ع الفاضي.
  • علاقتها بالـ Microservices (س42): الـ Microservices تحدد حدود وتقسيم الخدمات (Service boundaries)، بينما الـ Serverless توصف نموذج التشغيل والبنية التحتية (Execution & infrastructure model).
  • مشكلة الـ Vendor Lock-In (س43): صعوبة نقل التطبيق بين مزودي السحابة بسبب الاعتماد على خدمات وصيغ أحداث حصرية (Proprietary event formats).

⛓️ كشف التلاعب والإجماع في Blockchain (س44، س45، س46)

  • كشف التزوير (س44): كل كتلة ليها بصمة (Cryptographic hash) ومربوطة باللي بعدها؛ تعديل أي كتلة قديمة يغير الـ Hash بتاعها ويبوظ تطابق السلسلة كلها.
  • Proof of Stake (PoS) (س45): اختيار المدققين (Validators) لتأكيد الكتل بناءً على الحصة المحجوزة (Committed stake). (بينما PoW يعتمد على التعدين والطاقة).
  • بلوكتشين الشركات (س46): لما نقيد التحقق على مؤسسات معتمدة مسبقاً، دي شبكة بتصريح (Permissioned participation model).

🎓 الشهادات، المحفظة، والـ Web3 (س47، س48، س49، س50)

  • بصمة الشهادة (س47): تسجيل الـ Cryptographic fingerprint للشهادة على البلوكتشين هدفه التحقق من أن الشهادة المقدمة تطابق البصمة المسجلة (مش إثبات صحة الكلام جواها).
  • دور المحفظة Wallet (س48): إدارة مفاتيح التشفير والتوقيع لاعتماد المعاملات (Manage cryptographic keys and authorize transactions).
  • حقيقة تطبيقات Web3 (س49): لو استخدم عقود ذكية بس بواجهة مستضافة مركزياً ومزود بيانات واحد، يبقى فيه مكونات لامركزية بس لسه عنده اعتماديات مركزية (Centralized dependencies).
  • المعمارية الهجينة (س50): نجمع Microservices (لتقسيم الخدمات) + Serverless (لتشغيل الأحداث) + Blockchain (لتوثيق السجلات المشتركة) لأن كل تقنية بتحل متطلب مختلف.
